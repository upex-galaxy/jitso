# Decisions

What was decided for JITSO and this repo, the options each decision beat, and why. How the contract itself is built (runner, case format, status model) is recorded in `contract/PLAN.md`; per-behavior calls for the port are in `contract/TS-ODDITIES.md`.

To add a decision, append a row with the options it beat and the why. A reversed decision gets a new row that names the row it supersedes; the old row stays as history.

## Product and repo decisions

Decided by the owner on 2026-11-14.

| # | Decision | Options beaten | Why |
|---|---|---|---|
| D1 | The CLI is written in Go, from the new design, not translated line by line | a compiled TypeScript binary; TypeScript now and Go later; Rust | binary size (the compiled TypeScript CLI measured about 85 MB, a stdlib-only Go probe about 3 MB stripped), distribution as one file, hooks that need no Node or Bun, and the design changes anyway |
| D2 | JITSO has its own repository, kept local for now with no remote | create a private or public remote now | creating a remote is an outward step the owner has not taken yet |
| D3 | Contract tests first, then the port; the TypeScript implementation is the frozen oracle | finish the builds work in TypeScript first; write Go from scratch with no oracle | a contract the old and new binaries both run stops fixed bugs from coming back |
| D4 | Distribution through GitHub Releases, an install script and a Homebrew tap; an npm shim later | `go install` only | users who do not have Go |
| D5 | JITSO ships no builds: only patterns, a schema with validators, the hard-rules core, an authoring skill and empty templates; each project defines its own builds | ship generic builds | builds are specific to each project |
| D6 | The term is `build`, not `preset`. Builds are looked up in layers (the repo, then trusted parent folders, then the user), nearest wins, and are validated against the allowlists of the repo where they launch | keep `preset`; no parent-folder layer | monorepos and reuse across repos |
| D7 | Just-in-time builds are drafts validated by code, kept in a git-ignored folder; `jitso build save` promotes one only with the owner's OK | builds at user level only; never save a draft | keeps the allowlist guarantee for anything that launches |
| D8 | Adoption commands: `install skill --scope user\|project`, `setup hook`, `setup instructions` (a delimited, reversible block in the target's `AGENTS.md`) and `doctor`, each showing a diff and writing a backup | install the skill and the hook only | adoption in one command per step |
| D9 | Everything moves here first (code, the catalog patterns as templates, hooks, docs, the local history); only then is JITSO removed from the repo it came from, which becomes an ordinary consumer of the CLI; that repo's installer and updater do nothing with JITSO | keep a vendored copy in the original repo | less noise and an independent release cycle |

| Builds are looked up in layers, nearest first: the repo's `jitso/builds/`, then each trusted parent folder's `jitso/builds/` (the nearest parent first), then the user's `~/.jitso/builds/`. The layers are computed from the real path of the primary checkout, so a linked worktree gets the layers of its primary. Shadowing is by `id`: the nearest file that has an id is the build of that id, whether or not it is valid here, and a farther file with the same id is never used; inside one layer the first file by file name wins. A parent or user build needs `status: approved` like any other. `build list` ends a parent or user line with ` (from <layer> <path>)` (the dispatcher's catalog does not), the card header ends with ` (<layer>)`, and every registry launch line records `build_layer` (`repo`, `parent` or `user`), `build_file` (the real absolute path) and `build_sha256` (of the file's bytes). The draft layer joins the order later. Defect N-12 | first valid file wins; merge fields across layers | what the nearest layer says is what launches: a merge would build a profile no file shows, and "first valid" would let a broken near file silently hand the id to a far one |
| Trust is only the `trusted_parents` list of `~/.jitso/config.yaml` (`version: 1` optional; absolute paths or paths that start with `~/`). Entries are compared by real path (symlinks resolved, `..` cleaned); a parent counts only when the primary checkout's real path is strictly inside it, so the folder itself and its siblings, also those that share a name prefix, never match; the nearest (longest) parent comes first whatever the order of the file. `/`, `~` and HOME are refused, an entry that does not exist is skipped, a missing file means no trusted parent, and an invalid file is exit 3 for every catalog command (`jitso: ~/.jitso/config.yaml is invalid: <problem>`) because it changes which builds exist. A repository's own files are never read for trust, and a parent's own `jitso/jitso.yaml`, hard rules and drafts are never read. Defect N-12 | trust declared in the repo's `jitso.yaml`; walking every folder up to HOME | trust flows outside in: the user decides which folders may supply builds, so a repository cannot widen its own catalog or a sibling's. Trusting HOME or `/` would make every build of the machine a layer |
| The repo's own build files keep the whole-catalog rule: one invalid file is exit 3 for every catalog command. A parent or user file that is invalid for the launching repo is skipped instead: `build list` warns on stderr (`jitso: warning: skipped build <layer> <path>: <problems>`), `jitso launch --build <that id>` is rejected with exit 2 (`build "<id>" from <layer> <path> is invalid here: <problems>`), and every other command is silent. Defect N-12 | fail every command on an invalid file at any layer; skip it silently | a user build that is valid in one repo and not in another must not break the other repo, while the repo's own catalog keeps the strictness the contract pins. The warning and the rejection tell the owner which file to fix |
| Every build of every layer is validated against the repo that launches it: that repo's `jitso/jitso.yaml` allowlists and its `.agents/instructions/` route ids, and a worker's subagent names resolve with the same layered lookup from that repo (a user worker that lists `plan` gets the repo's `plan` when the repo has one). A repo without `jitso/jitso.yaml` has no allowlists, so every catalog command exits 3 (`jitso: jitso/jitso.yaml is missing: this project has no JITSO allowlists (create it with jitso build new <id>)`). Defect N-12 | validate a build against the folder it lives in | D6: a build is reused across repos, and the allowlists that bind a launch are the launching repo's. The same build can be valid in one repo and invalid in another |
| `jitso build validate [<id>]` checks builds without stopping at the first problem. It scans every layer tolerantly and prints one line per file (`<ok\|invalid> <id or -> <layer> <path>`, plus ` (shadowed by <layer> <path>)` when a nearer file has the id), each problem of an invalid file indented under it, and `checked <n> builds: <a> ok, <b> invalid`. With an id it prints only the winner of that id, its problems and the files it shadows, and counts the winner only; an id no file has is `JITSO REJECTED: unknown build "<id>"`. It reports the load rules plus the rules only a launch sees (a worker or conductor needs a `budget` mapping and a harness with an adapter, and every subagent it lists must be approved). An invalid file of the repo is a finding here (exit 2), not the exit 3 every other catalog command gives. Exit 0 when every counted file is ok, 2 when one is invalid or the id is unknown, 3 for the environment (no `jitso/jitso.yaml`, bad user config, outside git). It takes no flag. Defect N-13 | an `--all` flag; a `--json` output now | no argument already means every build, and a JSON output can come with `doctor` from the same scan. Failing like every other command on an invalid repo file would hide the other problems: this command exists to list them all |
| The hard-rules core and the reply style ship inside the binary (`internal/rules`, `go:embed`) and are the default only when a project has no `jitso/hard-rules/` folder. When the folder exists, both `core.md` and `style.md` are required (a missing one is exit 3 naming the file) and are used byte for byte, joined by one newline, with nothing prepended. The shipped core holds the rules every session needs in any project (credentials by name, scope, launching, discards, verification, budget, reporting, skills, JITSO's own files, nothing leaves the machine); project conventions such as commit trailers or the language of artifacts stay in a project's own folder. Defect N-14 | always prepend the embedded core to the project's files | `docs/architecture.md` already decided the embedded core as a default, and prepending would change the `core_sha256` and the join cases that pin the project's files. A project that has its own folder owns its rules completely, so it can also drop a shipped rule: whether to prepend instead is the owner's call, as a contract change of its own (recommendation: revisit after the builds work) |

A template carries `status: draft`, its tier and every allowlist-bound value empty, so a validator names each empty value until it is filled, and no template names a real model, skill or server. `jitso build new <id> [--tier worker|conductor|subagent]` writes the draft `.jitso/drafts/<id>.yaml` from the tier template (worker by default) and prints how to go on; it refuses the id of any saved build and the id of an existing draft, checking both before it writes anything, and never overwrites. Defect N-15 | commit drafts to the repo; a user-level drafts folder; rewrite the input (normalise it) before writing | a draft is scratch that an agent writes and a person reviews, so it belongs to the project that launches it but never to its history; keeping the bytes means the hash the registry records is the hash of exactly what the author wrote |

Defect N-15 | drafts nearest of all; drafts in a separate namespace; a draft may replace a saved build | an agent must not be able to shadow an approved build with its own draft under the same id, which would put unreviewed text where reviewed text was; the last-place rule makes that structural instead of a check |

| "Is a terminal" is a real isatty: `internal/tty` asks the kernel with the termios ioctl (`TIOCGETA` on macOS, `TCGETS` on Linux) and answers false on any other OS, for a pipe and for a regular file. `System.StdinIsTerminal` wires it to standard input. | `jitso build save <id> [--confirm <token>]` is the one way a build becomes approved, and it is the owner's. It checks the draft again against the current allowlists and the launch rules, refuses a draft whose `id` is not its file name, refuses when `jitso/builds/<id>.yaml` exists (the file is created exclusively, so it never overwrites, a dangling symlink included) or when any saved build of any layer has the id, and shows the bytes it would write, every line prefixed `+ ` (a control character is shown as `\xNN`, so a draft cannot hide text from the person who reads it). The bytes are the draft with the top-level `status` scalar `draft` replaced by `approved`: the position comes from the YAML node (`catalog.StatusSpan`) and is checked against the decoded value, every other byte is kept, a quoted status keeps its quotes, and a status written with a tag, an anchor, an escape or over several lines is refused as not savable in place. On a terminal it asks `[y/N]` and only `y` or `yes` saves; without one it refuses (exit 2) and prints the token, the first 12 hex characters of the SHA-256 of the bytes it would write, which `--confirm` must repeat, so the OK is bound to the content that was read. The draft is removed after the write. Defect N-15 | saving only on a terminal; writing `status: candidate` and asking for a second edit to approve; relying on the token as the guard | the contract runner never gives a terminal, so `--confirm` is the one success path the contract can run, and the terminal path is unit-tested with an injected terminal and reader; `candidate` would put an unreviewed edit between the owner's OK and the approved file; a token is not a secret (anyone who can read the draft can compute it), it ties an OK to a content, not to a person |

The match is on text, so a commit message that holds those words is denied too (accepted). Honest limits, for the owner: neither the guard nor the token stops a session without the hook, a pseudo-terminal that fakes a terminal, or a Write, Edit or `cp` of a file into `jitso/builds/`, which skips `save` altogether; git review and the commit rule are the last line. A later change can make the guard deny Write and Edit under `jitso/builds/`, `jitso/jitso.yaml` and `jitso/hard-rules/` (an `ask`). Defect N-15 | relying on the token; matching only a segment that starts with the launcher, as the launch deny does; matching by program path instead of text | an agent can read the draft and compute the token, so only the hook stops it; a first-word match misses `sh -c '...'`, which is exactly the form an agent reaches for; a path match misses a launcher spelled any other way. The text match costs a false positive on a commit message, which is cheaper than a form that slips through |
| No machine-readable JSON Schema is shipped. The schema is `docs/build-schema.md` plus the validators | ship a JSON Schema | what a build may name depends on each project's allowlists and instruction sections, which a static schema cannot express, and a second copy of the rules would drift. A schema generated from the same rule table can come later |

Defect N-21 | a commit and a date stamped with `-X`; `main.version` as the variable; JSON output | a build without a date is reproducible for the same toolchain, flags and commit; the Go toolchain already records the commit, so only the version needs a stamp, and `go install <module>@<tag>` gets the tag from the module version; `main` is wiring only (`docs/architecture.md` section 3) and the command layer needs the value |

## The contract-first rule

A behavior change starts as a case under `contract/cases/`. Behavior the oracle already has is pinned as `pass` for both implementations. Behavior the oracle lacks is written as the intended behavior with `status: {"ts": "xfail", "go": "pass"}`, a `defect` id and an `intent`. The Go port must pass every case. When the oracle and a case disagree, the oracle wins unless the behavior is a listed defect or a `TS-ODDITIES.md` row the owner decided. The procedure is the `contract-driven-development` skill; the format is `contract/SPEC.md`.

## Known defects of the oracle

Measured against the TypeScript implementation on 2026-11-14. Each is encoded as intended behavior, `xfail` on `ts` and `pass` on `go`; the cases are the ones that declare `status.ts: xfail` (`grep -rl '"xfail"' contract/cases`). N-2 to N-4 are decided TS-ODDITIES rows (L2, L3, L8, owner, 2026-11-15). N-5 to N-8 come from the owner's decisions of the same day (the tier model, the dispatcher project handoff, the launcher word of the dispatcher prompt). N-9 is a hardening found while validating the launcher path (decided inside the completion wave, a technical call). N-10 is the rename of D6 made in the contract: it renamed the flag, the folder and the command that the earlier rows of this table name (`--preset`, `presets/`, `presets list`), and those rows stay as written, so read them as `--build`, `builds/` and `build list`. N-12 is the layered lookup of D6 (the repo, trusted parent folders, the user folder). N-15 is the draft half of D7 (the draft layer, the commands that fill and empty it, and the save that approves one).

| Id | Intended behavior | The oracle today |
|---|---|---|
| S1 `route_scope` | the launch card has six lines, with `ROUTE-SCOPE: <ids>` (the colon the router's regex needs) on a line of its own after the subagents line, and in `direct` mode the first prompt carries the same line | the card has five lines and writes `ROUTE-SCOPE` without the colon, as the tail of the subagents line; the first prompt only says to read the brief |
| S2 `agents_md` | a build with `agents_md: exclude` launches `claude` with `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` in its environment | the field is only logged. Measured on Claude Code 2.1.325 in a headless canary test: the variable stops both the native read of a lone `AGENTS.md` and a `CLAUDE.md` that imports `@AGENTS.md`. Not covered: user-level instruction files, nested or parent folders, other versions or models |
| S3 `subagents` | a worker build's `subagents` reach `claude` as `--agents <json>` with exactly those keys, each entry carrying the `description`, `prompt`, `model` and `tools` of the build (tier subagent) of that name | no `--agents` flag is ever passed |
| N-1 project root | the project is the git primary checkout of the working directory; outside a git checkout the command exits 3 | the oracle finds its project from its own script folder |
| N-2 failed launch | a launch that fails before its registry line leaves no `.jitso/launches/<id>/` folder behind (TS-ODDITIES L2) | the folder (brief, card, core, mcp.json, run.sh) stays on disk with no registry line, so `reap` never sees it |
| N-3 trust timeout | a trust dialog that never clears still exits 0 and registers the launch, and prints a warning on stderr that names the trust dialog and says it did not clear (TS-ODDITIES L3; beaten: exit 3 and close the terminal) | exit 0 and the registry line, with nothing on stderr |
| N-4 modes | only `direct` and `fleet` exist, on the command line and in registry lines; `directo` and `flota` are rejected (exit 2) and a registry line with either is an invalid line (TS-ODDITIES L8; beaten: read old lines but reject on input, keep both) | both aliases are accepted, normalized to the English mode, and read from old registry lines |
| N-5 tiers: launch and listing | a subagent-tier build is not launchable alone (`launch --preset plan` exits 2 with `JITSO REJECTED:` naming the tier) and is not shown by `presets list` or offered in the dispatcher catalog | the oracle has no tiers: it launches and lists every approved preset |
| N-6 tiers: subagent names | a worker whose `subagents` names a missing build, or a build that is not subagent tier, is a catalog error (exit 3, stderr names the file and the subagent) | the oracle only checks that each name is kebab-case |
| N-7 dispatcher project handoff | `JITSO_PROJECT` names the project: set to a git checkout it lets a launch run from outside git, set to a folder that is not a git checkout it exits 3 naming the folder, and the dispatcher starts `claude` with it set | the oracle finds its project from its own script folder and never reads the variable |
| N-8 dispatcher launcher word | the dispatcher prompt's launch line starts with the launcher itself (no `bun` word) and is the line the dispatch guard allows | the oracle's guard allows only `bun <index.ts> launch`, so the line the new prompt template tells the model to write is denied |
| N-9 quoted words | the dispatch guard accepts a single-quoted word only where a space needs it, only for the launcher and the value of `--brief`; the dispatcher prompt writes the launcher quoted when its path holds a space, and the dispatcher refuses to start (exit 3) when the launcher path has characters the guard cannot allow | the oracle's guard denies every line that holds a quote, so a binary under a path with a space can never launch |
| N-10 build vocabulary | the launch flag is `--build`, the catalog folder is `jitso/builds/`, the catalog commands are `jitso build <subcommand>`, and every message, the card header and the usage say build; `--preset`, `presets` and `jitso/presets/` are unknown (D6, and the no-alias row of the other decisions). The registry log keeps its `preset` and `preset_version` keys | the oracle says preset everywhere: `--preset`, `jitso/presets/`, `presets list`, `unknown preset "<id>"`, `| preset <id> v<n>` on the card, `--preset` in the guard texts and in the dispatch guard's flag list. The cases reach it through a one-direction mapping in the ts adapter, so only the cases that pin renamed output are `xfail` |
| N-11 tier fields | a subagent-tier build needs no launch-only field (`route_scope`, `success`, `budget`, `mode_default`, `agents_md` and `harness` are optional), must leave `skills_first`, `mcp`, `requires` and `subagents` empty, and a worker may launch only with approved subagents (exit 2, `JITSO REJECTED: build "<worker>" lists subagent "<subagent>", which is <status>, not approved`) | the oracle validates every file as a worker preset, so it requires `route_scope` and `success` of a subagent-tier build, accepts the lists, and ignores a subagent's status |
| N-12 build layers | builds come from layers, nearest first: the repo's `jitso/builds/`, each trusted parent folder's `jitso/builds/` (the folders `~/.jitso/config.yaml` trusts that contain the repo), then `~/.jitso/builds/`; the nearest file of an id is the build, every build is validated against the launching repo's allowlists and route ids, one that is invalid there is skipped (a warning in `build list`, a rejection at launch), and `build list`, the card and the registry launch line name the layer (`build_layer`, `build_file`, `build_sha256`); without `jitso/jitso.yaml` every catalog command exits 3 and says what to create | the oracle reads only the repo catalog: no parent folder, no user folder, no user config, no origin anywhere, and it fails with its own error text when `jitso/jitso.yaml` or the builds folder is missing |
| N-13 build validate | `jitso build validate [<id>]` reports every problem of every build file of every layer (the load rules and the launch rules: budget, harness adapter, approved subagents), one line per file and a summary line; exit 0 all ok, 2 any invalid or an unknown id, 3 environment (see the other decisions) | the oracle has no `build` command (and the contract runner maps only `build list` for it): it answers `unknown command` with exit 2, and it can only fail on the first invalid file of a launch or listing |
| N-14 shipped core and templates | with no `jitso/hard-rules/` folder, `core.md` of a launch is the hard-rules core and the reply style shipped inside the binary, joined by one newline, and `core_sha256` is the hash of that text; the build templates and the `jitso/jitso.yaml` skeleton are embedded, drafts whose empty allowlist-bound values keep them invalid until filled, and `jitso build new <id> [--tier <tier>]` writes one as a draft (see the other decisions) | the oracle requires the two project files and fails (exit 3, `ENOENT`) when they are missing; it ships no core and no templates, and `build new` is an unknown command (the runner maps only `build list`) |
| N-15 drafts | a just-in-time build is a draft: `jitso build draft <file.yaml\|->` checks it with the rules of the draft layer and keeps its bytes in `.jitso/drafts/<id>.yaml` (a folder that holds its own `.gitignore`), `jitso build list --drafts` shows the drafts, `jitso build discard <id>\|--all` deletes them, and `jitso launch --build <draft id>` launches one with `(draft)` on the card and `build_layer: draft` in the registry. `status: draft` is valid only in that layer, a draft never shadows a saved build, and a saved worker may not list a draft subagent. `jitso build save <id>` writes the draft as an approved build only with the owner's terminal OK or the token of the content he read, and the launch guard denies the command to agents (see the other decisions) | the oracle has no drafts and no `build draft`, `build list --drafts`, `build discard` or `build save`: each is an unknown command (the runner maps only `build list`), a launch of a draft id is `unknown preset`, and its guard knows no `jitso build save` verb: it stays silent |
| N-21 version | `jitso version` and `jitso --version` print one line with the version, the commit, the Go version and the platform and exit 0; `version x` exits 2 with `jitso version: takes no arguments`; the usage lists a `version` row | the oracle has no `version` command and no `--version` flag: both are an unknown command (exit 2, the usage on stderr) |
