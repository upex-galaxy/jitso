# Decisions

What was decided for JITSO and this repo, the options each decision beat, and why. How the contract itself is built (runner, case format) is recorded in `contract/PLAN.md` and `contract/SPEC.md`.

To add a decision, append a row with the options it beat and the why. A reversed decision gets a new row that names the row it supersedes; the old row stays as history.

## Product and repo decisions

Decided by the owner on 2026-11-14.

| # | Decision | Options beaten | Why |
|---|---|---|---|
| D1 | The CLI is written in Go, from the new design, not translated line by line | a compiled TypeScript binary; TypeScript now and Go later; Rust | binary size (the compiled TypeScript CLI measured about 85 MB, a stdlib-only Go probe about 3 MB stripped), distribution as one file, hooks that need no Node or Bun, and the design changes anyway |
| D2 | JITSO has its own repository, kept local for now with no remote | create a private or public remote now | creating a remote is an outward step the owner has not taken yet |
| D3 | Contract tests first, then the port; the TypeScript implementation is the frozen oracle | finish the builds work in TypeScript first; write Go from scratch with no oracle | a contract the old and new binaries both run stops fixed bugs from coming back |
| D4 | Distribution through GitHub Releases, an install script and a Homebrew tap; an npm shim later | `go install` only | users who do not have Go |
| D5 | JITSO ships no builds: only patterns, a schema with validators, the hard-rules core, an authoring skill and empty templates; each project defines its own builds | ship generic builds | builds are specific to each project |
| D6 | The term is `build`, not `preset`. Builds are looked up in layers (the repo, then trusted parent folders, then the user), nearest wins, and are validated against the allowlists of the repo where they launch | keep `preset`; no parent-folder layer | monorepos and reuse across repos |
| D7 | Just-in-time builds are drafts validated by code, kept in a git-ignored folder; `jitso build save` promotes one only with the owner's OK | builds at user level only; never save a draft | keeps the allowlist guarantee for anything that launches |
| D8 | Adoption commands: `install skill --scope user\|project`, `setup hook`, `setup instructions` (a delimited, reversible block in the target's `AGENTS.md`) and `doctor`, each showing a diff and writing a backup | install the skill and the hook only | adoption in one command per step |
| D9 | Everything moves here first (code, the catalog patterns as templates, hooks, docs, the local history); only then is JITSO removed from the repo it came from, which becomes an ordinary consumer of the CLI; that repo's installer and updater do nothing with JITSO | keep a vendored copy in the original repo | less noise and an independent release cycle |

## Other decisions

| Decision | Options beaten | Why |
|---|---|---|
| The project history lives in the git-ignored `.session/` folder and is never committed | commit it as is | it is private: other languages, tracker keys, raw notes |
| Release 1 targets macOS, Linux and Windows; Windows is marked "not tested" until the owner tests it | macOS only | cross-compiling is one environment variable |
| A subagent is a build with `tier: subagent`; Conductor, Worker and Subagent are the three tiers of the same Build, and a worker lists its subagents by name (decided 2026-11-15). Each project chooses the names (for example planner, implementer, tester, verifier). JITSO resolves them with the same layered lookup and allowlists and passes them to `claude` as `--agents`. A subagent-tier build cannot be launched alone with `jitso launch` | a separate `jitso/subagents/<name>.md` file format; inline definitions inside the worker's YAML; dropping the `subagents` field | one concept instead of two, matches the owner's model of tiers, and answers where each helper's `description` and `prompt` come from (defect S3) |
| The repo is licensed MIT (decided 2026-11-15) | Apache-2.0; no license until the model is decided | the same license the original repo declares, permissive and simple for adoption |
| The rename from `preset` to `build` (D6) happens in this repo, not in the original | rename in the original first | avoids renaming twice. The contract still says `--preset` and `presets/` because it pins the oracle; the rename is a contract change made with the port, cases first |
| The vocabulary is `build` wherever a user sees it, with no alias: the launch flag is `--build`, the catalog folder is `jitso/builds/`, and every message says build. `--preset`, `presets` and `jitso/presets/` are unknown to the Go CLI: the two words are rejected (exit 2) and the old folder is never read. The earlier row about the rename is carried out by defect N-10: the contract was renamed first, then the port | accept both spellings for one release | D6 says the term is `build`, and JITSO has no release or remote yet (D2), so there is nobody to migrate and an alias would be a second spelling to keep and to test for good. The oracle keeps the old spelling: the ts adapter maps the new spelling to it in one direction (`contract/SPEC.md` section 9), so the contract still cross-checks the oracle and only the cases that pin renamed output are `xfail` |
| The catalog commands are one command group, `jitso build <subcommand>`, whose first subcommand is `list`. `jitso build` alone exits 2 with the build usage on stderr, an unknown subcommand exits 2 the same way, and `--help` prints the usage and exits 0. The main usage lists the group as `build` with the summary `list, validate, create, draft, save and discard builds`, where `create` is `new` | `jitso builds list`; separate top-level verbs | one first word in the command table, room for the later verbs of the builds work (validate, new, draft, save, discard), and it settles the `presets` half of TS-ODDITIES C1: the old word is unknown instead of answering `not implemented yet` with exit 0 |
| The registry log keeps `preset` and `preset_version` as the keys of its `v: 1` lines. It is the one place the old word survives (flagged: it departs from the wording of D6; recommendation, the owner confirms) | rename to `build` and `build_version` with `v: 2`; rename and keep `v: 1` | a log key is a storage schema, not vocabulary: a rename makes every line already written invalid, so `close`, `reap` and `analyze` would silently lose the launches that are still running at the upgrade, and every case that seeds a registry line would turn `xfail`. A schema change deserves its own versioned change, with "close every running launch first" as the upgrade step |
| Tier matrix of a build: worker and conductor are validated identically. In a subagent-tier build `route_scope`, `success`, `budget`, `mode_default`, `agents_md` and `harness` are optional and unused (checked only when present), `description` and `prompt` stay required and non-empty, and `skills_first`, `mcp`, `requires` and `subagents` must be empty (`<field> must be empty in a subagent-tier build`, `a subagent-tier build cannot list subagents`). `budget` and `harness` of a worker are still checked at launch. The fixture's `sonnet-conductor` declares `tier: conductor` | forbid every launch-only field in a subagent-tier build now; validate a conductor differently from a worker | a subagent runs inside its worker's session and is never launched alone, so launch-only fields mean nothing to it and a lean file is what an author should be able to write. Forbidding them is not possible yet: the oracle validates every file as a worker preset and requires `route_scope` and `success`, so the fixture's subagent builds keep them while the oracle runs. Tightening to forbidden is the owner's call for when the oracle retires. Skills, MCP servers and required fields cannot be honored by a subagent, so accepting them would be a silent no-op, hence an error. Conductor and worker share one rule because the tier changes how a build is used, not what a valid launch needs |
| A worker may launch only with approved subagents: `jitso launch` of a build whose listed subagent is `candidate` or `retired` exits 2 (`JITSO REJECTED: build "<worker>" lists subagent "<subagent>", which is <status>, not approved`). A worker that lists no subagent is unaffected. The check runs at launch, not at catalog load | a catalog error (exit 3); no check | a subagent's prompt reaches `claude --agents` as reviewed text, and before this rule its `status` was validated and then ignored, so an unreviewed prompt reached the harness. A catalog error would fail every command while one subagent is being edited, so the gate sits where the text is used |
| Builds are looked up in layers, nearest first: the repo's `jitso/builds/`, then each trusted parent folder's `jitso/builds/` (the nearest parent first), then the user's `~/.jitso/builds/`. The layers are computed from the real path of the primary checkout, so a linked worktree gets the layers of its primary. Shadowing is by `id`: the nearest file that has an id is the build of that id, whether or not it is valid here, and a farther file with the same id is never used; inside one layer the first file by file name wins. A parent or user build needs `status: approved` like any other. `build list` ends a parent or user line with ` (from <layer> <path>)` (the dispatcher's catalog does not), the card header ends with ` (<layer>)`, and every registry launch line records `build_layer` (`repo`, `parent` or `user`), `build_file` (the real absolute path) and `build_sha256` (of the file's bytes). The draft layer joins the order later. Defect N-12 | first valid file wins; merge fields across layers | what the nearest layer says is what launches: a merge would build a profile no file shows, and "first valid" would let a broken near file silently hand the id to a far one |
| Trust is only the `trusted_parents` list of `~/.jitso/config.yaml` (`version: 1` optional; absolute paths or paths that start with `~/`). Entries are compared by real path (symlinks resolved, `..` cleaned); a parent counts only when the primary checkout's real path is strictly inside it, so the folder itself and its siblings, also those that share a name prefix, never match; the nearest (longest) parent comes first whatever the order of the file. `/`, `~` and HOME are refused, an entry that does not exist is skipped, a missing file means no trusted parent, and an invalid file is exit 3 for every catalog command (`jitso: ~/.jitso/config.yaml is invalid: <problem>`) because it changes which builds exist. A repository's own files are never read for trust, and a parent's own `jitso/jitso.yaml`, hard rules and drafts are never read. Defect N-12 | trust declared in the repo's `jitso.yaml`; walking every folder up to HOME | trust flows outside in: the user decides which folders may supply builds, so a repository cannot widen its own catalog or a sibling's. Trusting HOME or `/` would make every build of the machine a layer |
| The repo's own build files keep the whole-catalog rule: one invalid file is exit 3 for every catalog command. A parent or user file that is invalid for the launching repo is skipped instead: `build list` warns on stderr (`jitso: warning: skipped build <layer> <path>: <problems>`), `jitso launch --build <that id>` is rejected with exit 2 (`build "<id>" from <layer> <path> is invalid here: <problems>`), and every other command is silent. Defect N-12 | fail every command on an invalid file at any layer; skip it silently | a user build that is valid in one repo and not in another must not break the other repo, while the repo's own catalog keeps the strictness the contract pins. The warning and the rejection tell the owner which file to fix |
| Every build of every layer is validated against the repo that launches it: that repo's `jitso/jitso.yaml` allowlists and its `.agents/instructions/` route ids, and a worker's subagent names resolve with the same layered lookup from that repo (a user worker that lists `plan` gets the repo's `plan` when the repo has one). A repo without `jitso/jitso.yaml` has no allowlists, so every catalog command exits 3 (`jitso: jitso/jitso.yaml is missing: this project has no JITSO allowlists (create it with jitso build new <id>)`). Defect N-12 | validate a build against the folder it lives in | D6: a build is reused across repos, and the allowlists that bind a launch are the launching repo's. The same build can be valid in one repo and invalid in another |
| `jitso build validate [<id>]` checks builds without stopping at the first problem. It scans every layer tolerantly and prints one line per file (`<ok\|invalid> <id or -> <layer> <path>`, plus ` (shadowed by <layer> <path>)` when a nearer file has the id), each problem of an invalid file indented under it, and `checked <n> builds: <a> ok, <b> invalid`. With an id it prints only the winner of that id, its problems and the files it shadows, and counts the winner only; an id no file has is `JITSO REJECTED: unknown build "<id>"`. It reports the load rules plus the rules only a launch sees (a worker or conductor needs a `budget` mapping and a harness with an adapter, and every subagent it lists must be approved). An invalid file of the repo is a finding here (exit 2), not the exit 3 every other catalog command gives. Exit 0 when every counted file is ok, 2 when one is invalid or the id is unknown, 3 for the environment (no `jitso/jitso.yaml`, bad user config, outside git). It takes no flag. Defect N-13 | an `--all` flag; a `--json` output now | no argument already means every build, and a JSON output can come with `doctor` from the same scan. Failing like every other command on an invalid repo file would hide the other problems: this command exists to list them all |
| The hard-rules core and the reply style ship inside the binary (`internal/rules`, `go:embed`) and are the default only when a project has no `jitso/hard-rules/` folder. When the folder exists, both `core.md` and `style.md` are required (a missing one is exit 3 naming the file) and are used byte for byte, joined by one newline, with nothing prepended. The shipped core holds the rules every session needs in any project (credentials by name, scope, launching, discards, verification, budget, reporting, skills, JITSO's own files, nothing leaves the machine); project conventions such as commit trailers or the language of artifacts stay in a project's own folder. Defect N-14 | always prepend the embedded core to the project's files | `docs/architecture.md` already decided the embedded core as a default, and prepending would change the `core_sha256` and the join cases that pin the project's files. A project that has its own folder owns its rules completely, so it can also drop a shipped rule: whether to prepend instead is the owner's call, as a contract change of its own (recommendation: revisit after the builds work) |
| A new build starts from an embedded template (`internal/templates`: one per tier and the `jitso/jitso.yaml` skeleton) and is written as a draft, never into `jitso/builds/`. A template carries `status: draft`, its tier and every allowlist-bound value empty, so a validator names each empty value until it is filled, and no template names a real model, skill or server. `jitso build new <id> [--tier worker|conductor|subagent]` writes the draft `.jitso/drafts/<id>.yaml` from the tier template (worker by default) and prints how to go on; it refuses the id of any saved build and the id of an existing draft, checking both before it writes anything, and never overwrites. In a fresh project (no `jitso/jitso.yaml` and no `*.yaml` in `jitso/builds/`) it first writes the `jitso/jitso.yaml` skeleton, so the author has allowlists to fill; a project that has builds and no allowlists is broken, not new, and gets the missing-allowlists error (exit 3) with nothing written. The skeleton overlaps the adoption commands of D8: whether `doctor` or `setup` should own it later is the owner's call (an `ask`). Defect N-14 | write the template into `jitso/builds/`; a `jitso init` command; print the template to stdout only | an invalid file in `jitso/builds/` fails every catalog command, so a template written there would break the project until it is filled; a draft is skipped while invalid and reaches `jitso/builds/` only through `jitso build save`, with the owner's OK (D7). `init` would be an adoption command outside D8, and stdout alone leaves the author to create the file and the folder |
| Drafts live in `<primary>/.jitso/drafts/<id>.yaml`, a folder that is the project's, not the checkout's: a linked worktree writes to its primary. `jitso build draft` creates the folder and `.jitso/drafts/.gitignore` (the single line `*`) when they are missing, never rewrites an existing `.gitignore`, and writes through a temporary file renamed into place, so nothing outside the folder is touched and a symlink at the file name is replaced, never followed. A draft is the input bytes unchanged, at most 64 KiB, from a path ending in `.yaml` or `.yml` or from `-` (stdin), and it is always stored as `<id>.yaml`; the id must be kebab-case of at most 64 characters, because it becomes a file name. Defect N-15 | commit drafts to the repo; a user-level drafts folder; rewrite the input (normalise it) before writing | a draft is scratch that an agent writes and a person reviews, so it belongs to the project that launches it but never to its history; keeping the bytes means the hash the registry records is the hash of exactly what the author wrote |
| A draft is the last layer and never shadows a saved build: `jitso build draft` refuses an id any saved build of any layer already has (`JITSO REJECTED: build "<id>" already exists (<layer> <path>): a draft needs an id no build has`), whether or not that build is valid here, and a saved build that appears later wins the id while the draft stays on disk, shown as `shadowed by <layer> <path>` in `build list --drafts`. Re-drafting an id replaces that id's own draft. `status: draft` is the only status of a draft file and is invalid in every saved layer (`status must be draft in a draft`, and `status must be one of candidate, approved, retired` elsewhere). An invalid draft is skipped like an invalid outer-layer file: a warning on `build list`, a rejection at launch, silence elsewhere. Defect N-15 | drafts nearest of all; drafts in a separate namespace; a draft may replace a saved build | an agent must not be able to shadow an approved build with its own draft under the same id, which would put unreviewed text where reviewed text was; the last-place rule makes that structural instead of a check |
| `jitso launch --build <id>` launches a draft through the one lookup every build uses: the draft layer is searched last and a draft launches with status `draft`, the one place any status other than `approved` launches. It is validated against the allowlists like any build, its card header ends ` (draft)` and the registry line records `build_layer: draft`, the real path and the SHA-256 of the bytes, which stays in the log after the draft is discarded. A draft worker may list draft subagents; a saved worker may list only approved ones (`which is draft, not approved`), and a draft worker still may not list a candidate or retired one. A draft is never listed by `build list`, never offered in the dispatcher catalog and never launchable as a subagent-tier build alone. Defect N-15 | a separate `--draft <id>` flag; letting a saved worker list a draft subagent | one lookup and one flag. The separate flag would keep the dispatcher from launching a draft whose id it guesses; it is the stricter option, left to the owner if drafts need to be hidden from the dispatcher. A subagent's prompt reaches `claude --agents`, so a saved worker takes reviewed prompts only |
| The dispatcher cannot draft: its guard still allows Write only to `briefs/*.md` and Bash only the `launch` command, so `jitso build draft` and `jitso build discard` are denied to it | allow `build draft` and a Write of `briefs/*.yaml` in the dispatch guard | widening the most constrained session is the owner's call, not a technical one; drafting is for the sessions that already have a project checkout. |
| Drafts have no automatic expiry: they stay until `jitso build discard <id>` or `jitso build discard --all` (every `*.yaml` of the folder, `discarded <n> drafts`, 0 included; the `.gitignore` and any other file stay). `discard` needs the project only (it does not load the catalog), is not guarded, and checks its arguments, and that an id is kebab-case, before it deletes anything | a time-to-live from the file's modification time | the contract cannot set a file time, and a draft is local and ignored, so the cost of keeping one is clutter, never safety. `jitso doctor` can report their age later |
| "Is a terminal" is a real isatty: `internal/tty` asks the kernel with the termios ioctl (`TIOCGETA` on macOS, `TCGETS` on Linux) and answers false on any other OS, for a pipe and for a regular file. `System.StdinIsTerminal` wires it to standard input. A command that asks a person a question asks only when it is true (`jitso build save`) | "standard input is a character device" (`os.ModeCharDevice`) | measured: `/dev/null` is a character device, and the contract runner gives it to every step that has no `stdin` key, so that test would take a run with no terminal for one and prompt |
| `jitso build save <id> [--confirm <token>]` is the one way a build becomes approved, and it is the owner's. It checks the draft again against the current allowlists and the launch rules, refuses a draft whose `id` is not its file name, refuses when `jitso/builds/<id>.yaml` exists (the file is created exclusively, so it never overwrites, a dangling symlink included) or when any saved build of any layer has the id, and shows the bytes it would write, every line prefixed `+ ` (a control character is shown as `\xNN`, so a draft cannot hide text from the person who reads it). The bytes are the draft with the top-level `status` scalar `draft` replaced by `approved`: the position comes from the YAML node (`catalog.StatusSpan`) and is checked against the decoded value, every other byte is kept, a quoted status keeps its quotes, and a status written with a tag, an anchor, an escape or over several lines is refused as not savable in place. On a terminal it asks `[y/N]` and only `y` or `yes` saves; without one it refuses (exit 2) and prints the token, the first 12 hex characters of the SHA-256 of the bytes it would write, which `--confirm` must repeat, so the OK is bound to the content that was read. The draft is removed after the write. Defect N-15 | saving only on a terminal; writing `status: candidate` and asking for a second edit to approve; relying on the token as the guard | the contract runner never gives a terminal, so `--confirm` is the one success path the contract can run, and the terminal path is unit-tested with an injected terminal and reader; `candidate` would put an unreviewed edit between the owner's OK and the approved file; a token is not a secret (anyone who can read the draft can compute it), it ties an OK to a content, not to a person |
| The agent boundary of `build save` is the launch guard, not the command: `jitso hook guard` denies a Bash segment that holds the words `jitso build save` (the bare word, `bun run jitso`, a path ending in `jitso`, this binary's own path, after `NAME=value` words or a separator, inside `sh -c '...'`), with `JITSO: only the owner saves a draft as a build; ask the owner to run: <launcher> build save <id> (denied: jitso build save)`. `build draft`, `list`, `validate`, `discard` and `new` stay allowed; the dispatch guard already denies everything but its launch line. The match is on text, so a commit message that holds those words is denied too (accepted). Honest limits, for the owner: neither the guard nor the token stops a session without the hook, a pseudo-terminal that fakes a terminal, or a Write, Edit or `cp` of a file into `jitso/builds/`, which skips `save` altogether; git review and the commit rule are the last line. A later change can make the guard deny Write and Edit under `jitso/builds/`, `jitso/jitso.yaml` and `jitso/hard-rules/` (an `ask`). Defect N-15 | relying on the token; matching only a segment that starts with the launcher, as the launch deny does; matching by program path instead of text | an agent can read the draft and compute the token, so only the hook stops it; a first-word match misses `sh -c '...'`, which is exactly the form an agent reaches for; a path match misses a launcher spelled any other way. The text match costs a false positive on a commit message, which is cheaper than a form that slips through |
| The agent boundary of the adoption commands (D8) is the launch guard too (B4-12): `jitso hook guard` denies a Bash segment that runs `jitso setup` or `jitso install` with the detector of `build save` (the bare word, `bun run jitso`, a path ending in `jitso`, this binary's own path, after `NAME=value` words or a separator, inside `sh -c '...'`), unless a word after the command is the standalone `--dry-run`, because a dry run only reads. The reason is `JITSO: only the owner changes the JITSO setup; ask the owner to run it in a terminal (denied: jitso <verb>)`, with `<verb>` `setup` or `install`. `doctor` and `version` stay allowed, and the dispatch guard already denies everything but its launch line. The match is on text, so a commit message that holds those words is denied too (accepted, as for `build save`), and a `--dry-run` word of the same segment exempts it wherever it sits after the command (a quoted `--dry-run` of another segment never does). Defect N-19 | relying on `--yes` (an agent can type it); denying only `--remove` | `setup hook --remove` disables the guard while the session runs (the file watcher reloads hooks), `setup instructions` rewrites the files every session reads, and `install skill --scope user` writes outside the project, so each is the owner's. Denying only `--remove` leaves the others open; `--yes` is a flag, not a boundary. A dry run writes nothing, so an agent may preview a change and show it to the owner |
| The jitso usage skill ships inside the binary: its source is `internal/skill/jitso/` (`SKILL.md` with only `name` and `description` in its frontmatter, and `references/`), embedded by `internal/skill/skill.go` with a plain `//go:embed jitso` (no `all:`, so a dotfile is never embedded). A unit test fails when that folder holds a dotfile, a name that starts with `_`, a symbolic link or a `.jitso-skill.json`. Defect N-16 | `skills/jitso/` at the repo root (an embed needs the package to sit in the folder, so the root would need an importable package); `.agents/skills/jitso/` (the repo's own development skills live there and would mix with the shipped one) | the other embedded text (`internal/rules`, `internal/templates`) already lives in an internal package next to its code, which keeps the module's API internal; the text itself is written by a separate pass, and changing it later changes only the embedded bytes, so no case pins it beyond the frontmatter |
| An installed copy carries a manifest `.jitso-skill.json` next to `SKILL.md`: `v` (1), `skill` (`jitso`), `jitso_version`, `content_sha256` and `files`, one SHA-256 per file by slash path. `content_sha256` is the SHA-256 of the concatenation, in path order, of `<path>\x00<file hex>\n`. The manifest is not in `files` and is not embedded, and its paths must be clean relative paths inside the folder (a manifest that names another path is not trusted: the folder counts as not installed by jitso). The state of a folder is read from it: `absent`, `current` (the manifest is the shipped content and every file matches), `outdated` (every file matches its hash, the manifest is of another version of the skill), `modified` (a listed file differs or is missing, or an unlisted file is there) and `unmanaged` (no valid manifest). A new jitso that ships the same text keeps the manifest of the version that wrote the files. Defect N-16 | a version line in the frontmatter; an HTML comment in `SKILL.md`; comparing the files with the embedded copy only | the frontmatter holds only `name` and `description` (AGENTS.md section 8) and a comment would cover one file; the per-file hashes are what tells a hand edit from an old version, which no comparison with the shipped text can |
| `install skill` puts the real files in `.agents/skills/jitso/` (Codex and OpenCode read it) and a relative symbolic link `.claude/skills/jitso -> ../../.agents/skills/jitso` for Claude Code, which reads only `.claude/skills`; user scope is the same pair under `$HOME`. This is this repo's own convention (AGENTS.md section 8). When a link cannot be made (Windows without the right, or a file system without links) the plan says so first (`warning: this system cannot create symbolic links (<reason>); <path> gets a second copy of the skill`) and `.claude/skills/jitso` gets a second managed copy with its own manifest, handled like the real folder. The ability to link is probed in a scratch folder under the temporary folder, before any write. Defect N-16 | two copies always; a link only into the folder of the jitso binary; an absolute link target | one source of truth for the harnesses that follow links, and a relative target survives moving or cloning the project; the probe keeps the plan honest in a dry run, at the cost that a project folder on a file system without links, with a temporary folder on one that has them, is not detected until the write fails (then the command is exit 3 and names the backup, if any) |
| `install skill` never overwrites or removes a copy that was edited by hand or that jitso did not install, unless `--force`, and `--force` backs it up first. It shows what it would change, then `JITSO REJECTED: the jitso skill in <path> was edited by hand (<file>, ...); nothing written; run again with --force to replace it (a backup is kept)` (or `... is not a copy jitso installed (no .jitso-skill.json); ...`, `... (it is a link to <target>); ...`), exit 2; for `--remove` the last words are `to remove it`. An outdated copy is upgraded without `--force` (nothing was edited). `--force` also deletes every file that is not shipped, so the folder is exactly the shipped tree afterwards. ## The contract-first rule
